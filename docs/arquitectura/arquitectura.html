Qué pasa cuando el mesero presiona «Enviar», y por qué la cocina lo ve al instante sin recargar.

El aviso no lleva datos

Solo dice qué cambió:
{ "temas": ["comandas", "produccion"] }
Cada pantalla vuelve a pedir lo suyo con su sesión y sus permisos: un aviso nunca entrega algo que la persona no podría ver. Si se pierde la conexión, la pantalla se refresca sola cada 20 a 60 s.

¿Y si dos lo hacen a la vez?

La base los forma en fila y el segundo ve lo que hizo el primero. Si el gerente y el mesero presionan Enviar al mismo tiempo, la cocina recibe el pedido una sola vez; si dos cajeras cobran la misma cuenta, entra un solo pago. Hay pruebas automáticas que fuerzan estos casos.

Al cobrar

Caja registra el pagoLa base cierra la comandaLa mesa queda libreSale el ticket impreso

El ticket no se guarda: se genera de la comanda y sus pagos. Si la impresora no responde, se imprime desde el navegador y caja nunca se detiene.

Seguridad, datos y tecnologías

Cada capa revisa por su cuenta: aunque alguien se salte una, la siguiente lo detiene.

Seguridad en capas

1 · Red local y HTTPS

Solo los equipos del restaurante llegan al servidor. Nginx cifra todo; la API y la base no se abren a la red.

2 · Sesión

Contraseñas con bcrypt. JWT en una cookie que el JavaScript no puede leer. Cada sesión vive en la base: cerrar sesión o dar de baja corta el acceso al instante. 5 intentos fallidos y espera.

3 · Permisos por rol

La API revisa en cada petición que el rol tenga la casilla. Un cambio de permisos aplica desde la siguiente acción.

4 · La base revisa otra vez

Los triggers vuelven a revisar reglas y permisos. La app entra con un rol que no puede borrar tablas ni tocar la bitácora o los pagos.

5 · Bitácora
Quién hizo qué y cuándo. No se modifica ni se borra.
